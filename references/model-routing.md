# Capability-based Model Routing

Цель маршрутизации — минимальная стоимость при сохранении требуемого качества. Храни в проекте capability и effort, а не имя модели: доступность и характеристики моделей меняются быстрее project memory.

## Политика

- `mechanical`: форматирование, детерминированные преобразования, узкие проверки; обычно low/medium.
- `balanced_reasoning`: обычная реализация и анализ с ограниченным контекстом; обычно medium/high.
- `deep_reasoning`: архитектурные конфликты, несколько систем, неоднозначные требования, высокий consequence; обычно high/xhigh.
- `independent_review`: критичная проверка отдельным reasoning stream без подсказанного вывода; effort не ниже high.

Quality profiles:

- `economy`: допускает более дешёвый route только при детерминированной проверке результата;
- `balanced`: default, повышает capability при риске или неоднозначности;
- `maximum`: качество важнее стоимости, требуется усиленная проверка.

Modes:

- `native`: runtime сам выбирает исполнителя;
- `advisory`: Project Master фиксирует рекомендацию, но не утверждает, что переключение произошло;
- `delegated`: отдельный executor допустим, если независимая работа оправдывает startup/aggregation overhead.

Эскалируй capability при конфликтующих требованиях, повторных failures, security/permissions, необратимой миграции, production impact или необходимости независимого review. Не создавай несколько агентов ради формального параллелизма; делегируй только независимые задачи с непересекающимися write scopes и проверяемым результатом.

Команда `state.py route` записывает решение и причину в STATE/event log. Она не переключает модель сама и не является доказательством фактически использованной модели.
