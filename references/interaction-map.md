# Редактируемая карта взаимодействий продукта — 3.0

Карта отвечает на вопрос «как работают skills/компоненты продукта», не «какие этапы проходит Project Master». Не подставляй lifecycle вместо продукта. Храни карту в .project-master/workflows/*.drawio; это необязательный инструмент, когда handoffs и stops требуют явного контракта. В 3.0 process approval включает смысловой SHA карты и игнорирует layout; legacy 2.1 требует upgrade перед такой интеграцией.

## Когда нужна карта

Используй её для системы с несколькими skills/компонентами, где существенны передачи данных, ветвления или остановки. Для простой локальной задачи достаточно короткого контракта в component file. BPMN остаётся вариантом для бизнес-процессов с pools/lanes/events; не создавай одновременно BPMN и drawio для одного потока без конкретной причины.

Храни карту в `<PROJECT_ROOT>/.project-master/workflows/WF-001-<slug>.drawio`. На одной странице — один понятный сценарий, обычно 5–12 узлов. Это рекомендация для читаемости, не запрет более сложного сценария. Для детализации добавь страницы/отдельные карты со стабильными ID. Не копируй пример как якобы внедрённую архитектуру.

## Один источник истины

`.drawio` — одновременно редактируемая диаграмма и машинно-читаемый контракт. Никакого второго обязательного JSON или Markdown sidecar. XML может быть обычным или сжатым после сохранения редактором; скрипт читает оба варианта. При изменении сохраняй IDs, ручную геометрию и неизвестные свойства. Не перегенерируй карту ради цветов или перемещения блока.

В diagrams.net / draw.io пользователь открывает файл, перемещает блоки, меняет стрелки и через **Edit Data** редактирует поля `pm_*`. Labels в примере используют placeholders из этих полей. При добавлении нового блока укажи `pm_kind` и его контракт; новая стрелка без контракта не должна молча стать маршрутом продукта.

## Контракт узла и передачи

| Поле | Значение |
|---|---|
| `id` | Стабильный ID в XML, например `SK-001`, `GATE-001` |
| `pm_kind` | `trigger`, `skill`, `component`, `gate`, `external`, `outcome`; для стрелки — `transition` |
| `pm_name` | Понятное название действия/результата |
| `pm_status` | `PLANNED`, `IMPLEMENTED`, `VERIFIED`: проектирование ≠ реализация ≠ проверка |
| `pm_handler` | Ответственный skill, функция, адаптер или провайдер для skill/component/external |
| `pm_inputs`, `pm_outputs` | ID артефактов через запятую, например `request.context,change.plan` |
| `pm_implementation` | Project-relative путь к реализации, обязателен для IMPLEMENTED/VERIFIED исполняемого узла |
| `pm_evidence` | Project-relative пути к evidence через `;`, обязательны для VERIFIED |
| `pm_effect` | `READ` или `WRITE` для external |
| `source`, `target` | IDs узлов стрелки |
| `pm_mode` | `data` передаёт артефакт; `control` обозначает только переход |
| `pm_artifact` | Один ID артефакта для data: источник производит его, получатель принимает |
| `pm_when` | Условие ветки, обязательно для всех выходов ветвления |
| `pm_max_attempts` | Положительный целочисленный лимит retry-стрелки; цикл без ограничивающего перехода — ошибка |

ID артефакта — связь, не доказательство совместимости форматов. Реальный payload/schema, версия, idempotency key и исключения должны быть определены в реализации/контракте компонента, если сценарий от них зависит. Валидатор этого не угадывает. Несколько producer для одного входа допустимы как альтернативные маршруты; карта не описывает исполняемые AND/OR join semantics.

## Контракт остановки

Для gate обязательны:

- `pm_stop_type`: AUTHORIZATION, INPUT, MISMATCH, UNCERTAINTY, PROVIDER или RUNTIME_FAILURE;
- `pm_reason`: конкретная причина, не абстрактное «безопасность»;
- `pm_origin`: OWNER, PROVIDER, TOOL_POLICY, PROJECT_DECISION или HYPOTHESIS;
- `pm_basis`: решение/документация/правило, на котором основано ограничение; это ссылка для проверки человеком, не автоматически доказанный факт;
- `pm_blocks`: IDs конкретных downstream действий, которые сейчас недоступны;
- `pm_resume_when`: проверяемое условие продолжения;
- `pm_owner`: кто/что снимает стоп;
- минимум два явно обусловленных выхода: продолжение и альтернативный результат/ожидание/восстановление.

Отсутствие разрешения на production-запись не запрещает разрабатывать эту возможность, интерфейс, test adapter и проверки. Gate AUTHORIZATION может автоматически проверить ранее выданные полномочия; это не обязательный вопрос владельцу на каждом вызове. Действующее разрешение не расширяй и не считай бессрочным. Карта не заменяет ограничения инструментов и внешних сервисов.

Гипотезу о запрете провайдера сначала проверяй. Не превращай собственное предположение в исключение рыночной функции. Если функция недоступна действительно, зафиксируй impact и альтернативу; если только нет текущего права выполнить действие, стоп относится к этому действию, а не ко всему продукту.

При UNKNOWN/PARTIAL внешней записи останови повторную запись и сверяй ту же операцию; не запускай новую попытку с новым ID. Независимые read-only, тестовые и проектные действия могут продолжаться, если не зависят от неизвестного результата. Критерии успеха операции и коммерческой готовности различай.

## Команды

Команды read-only, не исполняют skills и не изменяют карту/state:

```bash
python3 scripts/workflow.py validate .project-master/workflows/WF-001-plugin.drawio --root <PROJECT_ROOT>
python3 scripts/workflow.py inspect .project-master/workflows/WF-001-plugin.drawio
python3 scripts/workflow.py compare .project-master/workflows/WF-001-plugin.drawio --baseline <PREVIOUS.drawio>
```

Для многостраничного файла укажи `--page <PAGE_ID>`. `--strict` превращает warnings в nonzero exit code. Ошибки формата дают exit 2, нарушения контракта — exit 1, корректный контракт — exit 0. `compare` не возвращает failure только из-за разницы: выводит IDs и изменённые поля. Перемещение/цвет/маршрут линии не меняют contract SHA-256; смысловые поля, подпись, соединения и IDs меняют. Это НЕ legacy approval hash 2.1: тот всё ещё включает BPMN/sidecars, но не новые drawio maps.

Validator проверяет: ссылки на узлы, producer/consumer IDs, полноту входов, достижимость результата, выходы стопов, ограниченность циклов и отсутствие пути к external WRITE без AUTHORIZATION gate. С `--root` он также проверяет наличие implementation/evidence files и запрещает выход ссылок за корень проекта.

Он НЕ доказывает выполнение условий, отсутствие обхода проверки в реальном коде, качество/неизменность evidence, исчерпывающие ветки, совместимость payload, коммерческий результат или фактическую готовность интеграции. VERIFIED на карте требует проверки evidence агентом/владельцем, а не только успешного запуска валидатора. Не выдавай карту за runtime orchestrator.

## После визуального редактирования

1. Проверь карту и сравни с предыдущей копией из Git. Не перезаписывай её на основании устаревшего текста.
2. Только layout/style изменены — никаких новых продуктовых решений и повторных approvals ради этого.
3. Меняются входы/выходы/ветки/стопы — сопоставь затронутые IDs с требованиями, контрактами и реализацией. Запиши конкретную delta.
4. Изменение явно поручено владельцем — используй эту инструкцию как источник решения в её точных границах; не требуй повторить формулу подтверждения. Новая существенная развилка, стоимость или опасная внешняя операция требуют своего решения.
5. Для legacy 2.1 применяй действующие state/approval механизмы; новый модуль не даёт права обходить stale approvals.

Пример: [WORKFLOW-plugin-example.drawio](../assets/templates/WORKFLOW-plugin-example.drawio). Это синтетический проект без owner data и секретов. Все узлы PLANNED намеренно; пример показывает scoped stops, read-back и bounded reconciliation, а не утверждает наличие таких skills в установленной системе.

Формат и редактор: [официальная XML reference](https://www.drawio.com/docs/reference/diagram-generation/), [shape data](https://www.drawio.com/docs/manual/shapes/shape-data/).
