# Память цели, стратегия роста и обратная связь — 3.0

Главный recovery invariant: после compaction/session/handoff восстанови **зачем существует проект**, не только «какой файл редактировали». Не меняй цель молча ради удобной реализации или красивой метрики. Новое сообщение владельца — источник решения и профессиональных данных; история предыдущих разрешений не является текущим grant на внешние действия.

MISSION — обязательная память цели в 3.0, отдельно от STATE execution path. Bootstrap создаёт private/MISSION.json с явно отмеченными неизвестными, upgrade — из рассмотренного определения; recover.py восстанавливает её первым. Git-ignored каталог содержит персональное обучение только этого владельца. VISION/ROADMAP не переписываются миграцией; конфликт согласуй по источнику решения. Gitignore не защищает уже tracked/force-added файлы: перед публикацией проверяй состав пакета.

## Два режима одной памяти

- **BUILD:** конечный проект. Цель — рабочий продукт и проверяемый полный сценарий. Готовый код, passing tests и подключение API сами по себе не означают достижение цели. `success_criteria` определяют приёмку. Метрики добавляй, если они действительно измеряют результат.
- **OPERATE:** повторяющаяся работа действующего агента. Нужны outcome metrics с единицей, целевым значением, периодом, источником и допустимой давностью. Успешный цикл не закрывает проект; проверяется прогресс за определённый период, затем корректируется следующий цикл. Число операций не подменяет полезный результат.

Переход BUILD → OPERATE — явное изменение миссии с сохранённой историей, не автоматическое действие при последнем закрытом component. Сам модуль не запускает циклы/расписания; future scheduler требует отдельного задания.

## От малого к большому

В памяти одновременно держи:

1. `goal` — текущую конкретную цель;
2. `long_term_direction` — возможную дальнюю перспективу, без обещания сейчас реализовать все этапы;
3. `current_increment` — ближайший полный полезный сценарий;
4. для каждого increment: `outcome`, `check`, `extension_seam` и `not_now`.

Рабочий цикл: минимальный полный сценарий → проверка на реальном примере → обратная связь/результат → следующая возможность → новая проверка. Сохраняй дешёвые границы роста: reusable logic отдельно от owner data, явные I/O contracts, адаптер окружения вместо жёсткой привязки всей бизнес-логики к UI конкретного агента. Не создавай заранее очереди, микросервисы, биллинг, абстрактный runtime и multi-tenancy лишь потому, что дальняя цель может стать приложением.

MVP уменьшает охват первой поставки, а не произвольно запрещает будущие возможности. Отложено ≠ не поддерживается ≠ невозможно. Ограничение провайдера/инструмента проверь; ограничение текущих полномочий не переносится автоматически в продуктовое ядро. Проверки безопасности остаются пропорциональными действию.

## Компактное восстановление

Если MISSION существует, выполни `mission.py ... show` до выбора следующего шага. Снимок всегда содержит цель, режим, дальнее направление, критерии успеха и ближайший increment. Он подгружает первые 10 метрик и 5 memory references, последние 5 adopted lessons и 3 proposed lessons, указывает количество остальных. Полная история хранится в том же JSON; при необходимости прочитай `show --full`, а не заставляй каждое resume тащить всю историю в prompt.

Потом прочитай/проверь legacy STATE по [recovery.md](recovery.md), активный контракт и только нужные references. Сопоставь следующий шаг с целью: какой результат он приближает и чем будет проверен. Missing/stale/unknown data не превращай в 0, успешное выполнение или провал цели.

Файлы проекта переживают сжатие диалога; автоматическую загрузку этих файлов вне invocation skill модуль гарантировать не может. Поэтому recovery правило обязательно в skill. Сохраняй checkpoint перед handoff, после решения владельца, значимого результата и перед рискованным действием. Репозиторная память также требует нормального backup/Git: она не защищает от удаления диска.

## Измерения

Метрика: `id`, `name`, `unit`, `operator` (`gte`, `lte`, `eq`), `target`, `window`, `source`, `max_age_hours`. Observation: `id`, `metric_id`, `value`, `status` (VERIFIED/UNVERIFIED), `source`, `period_start`, `period_end`, `observed_at` и `evidence` для VERIFIED. Даты — ISO 8601 с timezone, evidence — путь внутри проекта, без секретов. VERIFIED означает, что автор observation уже проверил источник; скрипт не делает за него аудит.

Для OPERATE выбери измеримый результат, а не автоматически один и тот же KPI для всех проектов. Например, полезно различать подтверждённые квалифицированные обращения, оплату, стоимость и срок обработки; конкретные targets задаёт реальная экономика/задача владельца, не выдуманные числа.

Скрипт сохраняет период, источник и hash evidence. Отсутствие measurement → NO_DATA, непроверенная запись → UNVERIFIED, старый период → STALE, изменённый evidence → EVIDENCE_CHANGED. `target_met` вычисляется только для актуального VERIFIED observation с неизменившимся evidence. Перечитывание старого отчёта не делает старый период свежим. `window` и корректность агрегации требуют review: арифметическое сравнение не доказывает правильность выборки, причинность, достаточность данных или бизнес-успех. Старое измерение с другой definition метрики/другим goal_id не используется молча для нового критерия.

## Обучение рабочего подхода

Это не переобучение весов модели. Это сохраняемая обратная связь и проверяемая адаптация поведения:

**Действие → наблюдаемый результат → сравнение с целью → feedback/экспертиза владельца → предлагаемый урок → следующая bounded проверка → принятие, уточнение или отклонение.**

Lesson хранит `id`, `statement`, `kind`, `support`, `source`, `applies_to`, `status`; для ADOPTED/RETIRED обязателен `decision_source`, для OBSERVED_RESULT — `evidence`. Типы: EXPERT_KNOWLEDGE, USER_PREFERENCE, PROCESS_LESSON, HYPOTHESIS. Основание: USER_EXPERT, USER_FEEDBACK, OBSERVED_RESULT, AGENT_HYPOTHESIS. Статусы: PROPOSED, ADOPTED, RETIRED. Не называй собственную догадку professional knowledge или VERIFIED result; не отменяй принятую практику только на основании новой гипотезы.

Владелец — профессиональный источник: сохраняй содержание, происхождение и область применимости знания, а не только реакцию «понравилось/не понравилось». Не своди экспертизу к пользовательскому вкусу. Если экспертное утверждение конфликтует с текущим кодом/API/evidence, покажи конфликт и проверь, не объявляя одну сторону правой автоматически.

Для изменения принятого урока добавь новый ID с `supersedes`; старый остаётся в истории. PROPOSED replacement не отключает принятую практику до решения. RETIRED закрывает прежний урок. Принятая гипотеза требует новой feedback/evidence записи; строка `decision_source` хранит источник, но сама не доказывает человеческое согласие. Даже ADOPTED правило не расширяет task scope/permissions и не заменяет текущую инструкцию владельца.

Все lessons project-local и принадлежат владельцу этой памяти. У другого пользователя — своя изолированная история; общего хранилища обучения, автоматического экспорта или синхронизации нет. Не меняй глобальный skill автоматически, не переноси личное обучение в другой проект или другим пользователям, не публикуй owner data. Личное обучение **не становится общим правилом после удаления имени владельца**. Изменение reusable механизма возможно только по отдельному поручению после анализа: выводом может стать улучшение механики, но не копирование личных знаний/истории. Эффект урока оценивай по goal/metrics и feedback, не по тому, что правило удалось сохранить.

Input JSON для init/revise/record/learn и evidence также создавай внутри приватного каталога или другого явно приватного owner storage. Сам `.gitignore` не защищает от `git add -f`, ручного копирования, облачного доступа или уже отслеживаемых файлов; перед публикацией reusable core проверяй состав Git. Для нужного владельцу backup приватной памяти используй отдельно выбранное хранилище, не публичный repository. Не загружай `show --full` в публичные issues/PR/логи.

## Детерминированные операции

Сначала подготовь definition/observation/lesson JSON по реальным данным. Пример definition — [MISSION-example.json](../assets/templates/MISSION-example.json), не пользовательское утверждение и не production config.

```bash
python3 scripts/mission.py --root <PROJECT_ROOT> init --file <DEFINITION.json> --source "Реальная инструкция владельца"
python3 scripts/mission.py --root <PROJECT_ROOT> show
python3 scripts/mission.py --root <PROJECT_ROOT> record --file <OBSERVATION.json> --expected-revision <N>
python3 scripts/mission.py --root <PROJECT_ROOT> learn --file <LESSON.json> --expected-revision <N>
python3 scripts/mission.py --root <PROJECT_ROOT> revise --file <NEW_DEFINITION.json> --source "Новая инструкция владельца" --expected-revision <N>
```

`init` не перезаписывает существующую миссию. `revise` сохраняет прежние цели/стратегию, observations и lessons, не очищает историю. `record`/`learn` не перезаписывают IDs. Чтение — read-only; сохранение — atomic replace с hash и exclusive lock; stale revision второго автора отклоняется. Это защита нового MISSION store, не обещание исправленной конкурентности legacy STATE. После process crash может остаться `MISSION.lock`: проверь отсутствие активного writer и целостность файла перед явно согласованным снятием lock. Не удаляй lock автоматически.

Ошибка записи не должна вести к «обнулению памяти». Ошибка integrity требует восстановления/сверки сохранённой копии; старые observations/lessons не легализуются новым checksum молча. JSON не заменяет Git backup и не является защищённым криптографическим аудитом.
